LOKALT
assistentens gränser

Ett konto, låst vid start — inget verktyg tar emot "vilken användare". Rättighetsintyg måste skickas uttryckligen och vägrar som standard. Lässkommandon kan aldrig spendera kredit.

AKTIV

Vad som skyddar krediterna

huvudboken

Saldot lagras aldrig — det räknas fram ur en append-only-huvudbok. Ett lagrat saldo kan ändras med ett UPDATE; en summa kan inte.

AKTIV
reservationer

Krediten hålls vid start, debiteras vid lyckat jobb. Ett misslyckat jobb kostar aldrig något — det finns exakt ett anrop i hela systemet som debiterar en kund.

AKTIV
prisvalidering

Priset kommer aldrig från webbläsaren. Annars kunde vem som helst prenumerera på Studio för en krona.

AKTIV
idempotens

Nyckeln är (prenumeration, periodstart) — aldrig event-id. Stripe levererar samma faktura med olika id, så en dubbelutdelning vore annars gratis pengar varje månad.

AKTIV
radlås

Användarraden låses innan saldot läses. Utan det gick tre samtidiga jobb igenom på ett saldo som räckte till ett — hittat av ett test som försökte göra just det.

AKTIV
RLS

Row-level security: en fråga kan inte nå ett annat konto ens om applikationslogiken har fel. Gäller rollen appen faktiskt kopplar upp som — det var en riktig bugg en gång.

DRIFT
Nästa steg
  • Nu: gå igenom designen. Säg vad som ska ändras.
  • Sedan: säkerhetsgranskning — front door (inloggning, sessioner, rate limits) och back door (kreditförfalskning, RLS, tokens, SSRF).
  • Den granskningen ska köras som angripare, inte som utvecklare. Samma metod som hittade sex riktiga fel i gren A+B.
